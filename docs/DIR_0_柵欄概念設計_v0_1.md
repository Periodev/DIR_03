# DIR：柵欄概念設計

- 版本：v0.1
- 狀態：概念驗證中
- 用途：第二區碰撞關卡、資料結構與 Codex 實作參考

## 一句話定義

**柵欄是位於兩個相鄰網格之間的邊界：阻擋玩家與方塊的位移，但允許玩家跨越該邊界，對另一側的相鄰方塊安裝方向。**

核心目的不是新增一種普通障礙，而是把：

- 可接近
- 可操作

拆成兩件事。

玩家可以在執行區外預先設定方塊，但不能進入執行區重新推動、重新安裝或親自接手解法。

---

## 1. 問題背景

### 1.1 碰撞轉角為何難以成立

目前碰撞轉角關卡的主要漏洞，不是碰撞規則本身，而是碰撞接觸點通常位於開放空間。

原本預期流程：

```text
預先安裝
→ 碰撞改變方塊位置
→ 原方向在新位置生效
```

常見替代解：

```text
玩家走到碰撞後的位置
→ 重新安裝方向
→ 親自完成轉角
```

因此真正需要限制的不是「碰撞能否發生」，而是：

> 碰撞之後，玩家是否仍能進入接觸區並重新介入。

柵欄提供的正是：

> 能先安裝，但不能進入。

---

## 2. 已確認規則

柵欄位於兩個格子之間，不占據完整格子。玩家與方塊仍只存在於正常 cell 上。

### 2.1 行為表

| 行為 | 穿過柵欄 | 說明 |
|---|---:|---|
| 玩家移動 | 否 | 玩家不能跨越柵欄進入相鄰格。 |
| 玩家推動 | 否 | 玩家不能隔著柵欄直接推動方塊。 |
| 方塊觸發移動 | 否 | 已安裝方向的方塊不能穿越柵欄。 |
| 碰撞造成位移 | 否 | 被撞方塊不能被推過柵欄。 |
| 安裝方向 | 是 | 玩家可對柵欄另一側的相鄰方塊安裝方向。 |
| 遠端觸發 | 不受影響 | Trigger 本來就不依賴玩家鄰接。 |

規則摘要：

> **柵欄阻擋實體，不阻擋方向安裝。**

### 2.2 空間語彙

- **開放區**：玩家可移動、推動、安裝並重新介入。
- **柵欄邊**：玩家不可跨越，但可以安裝另一側的相鄰方塊。
- **封閉執行區**：方塊可以被預先設定與遠端觸發，但玩家不能進入接手。

---

## 3. 關卡設計價值

### 3.1 直接解決的問題

1. **切斷重新介入**  
   碰撞後的位置可被設計成玩家永遠無法抵達，因而不能補推或重新安裝。

2. **讓碰撞成為必要**  
   某方塊只有被另一塊撞到正確工位後，原先安裝的方向才有作用。

3. **簡化牆型**  
   不必再以複雜死角、狹道和玩家站位，勉強封鎖替代解。

4. **提高因果可讀性**  
   玩家能直接讀出：先設定、再碰撞、最後自行完成。

5. **建立工廠／流水線模式**  
   玩家位於工作走道或控制區，先對生產線內的方塊設定方向，再讓碰撞和 Trigger 依序執行。

### 3.2 適用範圍

柵欄適合處理：

- 玩家能走到碰撞接觸點。
- 玩家能抵達碰撞後的位置。
- 玩家能進入後續工位重新安裝。
- 玩家能親自補推，取代預期的碰撞流程。

柵欄不一定能處理：

- 玩家可從另一側推入。
- 玩家可提前安裝另一套方向。
- 其他方塊能形成替代碰撞鏈。
- 關卡存在完全不同的繞路。

因此柵欄不是所有碰撞問題的通用答案，而是精確處理：

> **玩家能親自接手碰撞流程。**

## 4. 最小原型：柵欄彈射／碰撞接力

```text
AB.C*
---##
@D..#
```

符號：

- `A`、`B`：需要預先安裝 `→` 的方塊。
- `C`：最後被推上目標的方塊。
- `D`：產生 `→` queue 的操作塊。
- `---`：位於上下兩排之間的水平柵欄。
- `*`：目標。

### 預期解法

1. 推動 `D` 取得 `→`，隔欄安裝到 `A`。
2. 再推動 `D` 取得第二個 `→`，隔欄安裝到 `B`。
3. Trigger `A`：`A` 碰撞 `B`，使 `B` 右移到下一個工位。
4. Trigger `B`：`B` 保留原本的 `→`，碰撞 `C`。
5. `C` 被推到最右側目標。

狀態示意：

```text
AB.C*  →  A.BC*  →  A.B.C
初始       B 被撞移    C 到達目標
```

這個原型同時展示：

- 隔欄安裝。
- 有向塊被碰撞後仍保留方向。
- 碰撞位置轉移。
- 流水線式碰撞接力。
- 玩家無法進入上排補推或重排工位。

### 是否需要純柵欄教學關

目前傾向：**不必。**

上述彈射關已足夠單純，柵欄和彈射互相解釋：

- 因為玩家不能進入，所以必須先隔欄設定。
- 因為方塊已預先設定，碰撞後才能繼續執行。

## 5. 第二區導入位置（暫定）

柵欄不宜在第二區開頭出現，否則玩家可能先把該區理解成隔欄遙控區，而不是碰撞區。

較自然的順序：

| 順序 | 關卡概念 | 教學目的 |
|---:|---|---|
| 1 | 直接碰撞 | 建立定－動碰撞的基本結果。 |
| 2 | 直接碰撞＋交錯折返 | 把碰撞放進既有操作序列。 |
| 3 | 對位碰撞 | 理解碰撞前要先創造對位。 |
| 4 | 轉移碰撞 | 碰撞目標或碰撞位置發生轉移。 |
| 5 | 空塊連續碰撞 | 展示連續碰撞鏈。 |
| 6 | 空塊連續碰撞＋延後拉回 | 加入時間與順序壓力。 |
| 7 | **柵欄彈射** | 首次引入「可安裝、不可進入」與流水線模型。 |
| 8 | **柵欄碰撞 L 轉** | 用柵欄切斷玩家親自接手轉角的替代解。 |
| 9 | 複合關 | 整合方向分散、L 轉和柵欄碰撞轉向。 |

## 6. 邏輯分層

柵欄位於 cell 之間，因此建議把資料分成三類：

```text
Terrain layer
- floor
- wall
- goal
- 其他格子屬性

Object layer
- player
- blocks
- block.vector

Edge layer
- fence
- 未來可能的 door / one-way edge / breakable edge
```

地圖外圍固定全部使用牆，因此 edge layer 只需保存內部相鄰格之間的邊。

若地圖為 `m × n`，內部邊界數為：

```text
(m - 1)n + m(n - 1)
= 2mn - m - n
```

---

## 7. 邊界資料方案

目前考慮兩種主要方案。

### 7.1 方案 A：二項邊陣列

分別保存水平邊與垂直邊：

```text
horizontal_edges[(m - 1), n]
vertical_edges[m, (n - 1)]
```

> 實際索引方向可依目前 row/column 慣例調整；重點是水平邊與垂直邊分開保存。

優點：

- 每條邊只保存一次。
- 資料量正好等於內部邊界數。
- 適合 runtime、碰撞判定與 BFS verifier。
- 不會把 cell、edge、corner 混成同一套遊戲座標。
- 未來可由 `bool` 升級為 `EdgeType`。

缺點：

- 水平邊、垂直邊與 cell map 尺寸不同。
- 手寫 ASCII 關卡較不直觀。
- 編輯器要區分正在編輯哪一種邊。

### 7.2 方案 B：擴張格邊地圖

將原始 cell、邊與角點放進同一個展開矩陣：

```text
A | B
--+--
C | D
```

原始 `m × n` 地圖展開後為：

```text
(2m - 1) × (2n - 1)
```

座標語意：

```text
偶列、偶欄：cell
偶列、奇欄：垂直邊
奇列、偶欄：水平邊
奇列、奇欄：corner
```

優點：

- ASCII 位置直觀。
- 適合手工造關。
- 編輯器可直接畫線。
- 邊有自然的視覺座標。
- 未來若增加門、單向邊或角點裝置，擴充方便。

缺點：

- 座標面積接近四倍。
- corner 目前沒有遊戲用途。
- runtime 若直接使用展開座標，移動一步會變成跨兩個索引。
- 容易讓遊戲邏輯混入呈現座標。

### 7.3 建議混合架構

兩種方案不必互斥：

```text
擴張格 ASCII／關卡編輯器
            ↓ parser
Terrain + Objects + HorizontalEdges + VerticalEdges
            ↓
遊戲 runtime + BFS verifier
```

建議：

- **作者格式／編輯格式**：擴張格邊地圖。
- **執行格式／驗證格式**：二項邊陣列。

這樣同時保留：

- ASCII 可讀性。
- runtime 邏輯正規化。
- verifier 的單一判定來源。

## 8. 實作介面建議

所有移動和互動應統一經過邊界查詢，不要讓玩家移動、推動、Trigger 和碰撞各自實作一套柵欄判定。

```csharp
public enum EdgeType
{
    Open,
    Fence,
}

public enum MoveKind
{
    PlayerMove,
    Push,
    TriggeredMove,
    CollisionMove,
}

public EdgeType GetEdge(Vector2I cell, Vector2I direction);

public bool CanCrossEdge(
    Vector2I cell,
    Vector2I direction,
    MoveKind moveKind
);

public bool CanInstallAcrossEdge(
    Vector2I cell,
    Vector2I direction
);
```

柵欄的預設結果：

```text
CanCrossEdge(...)         = false
CanInstallAcrossEdge(...) = true
```

注意：

- Terrain / Object / Edge 邏輯資料應是唯一真實來源。
- Godot `TileMapLayer` 只負責呈現。
- 外圍牆由 terrain layer 保證，不必重複保存在 edge layer。
- 若未來加入門、單向邊或可破壞邊界，再擴充 `EdgeType`。

## 9. 視覺與玩家心智模型

### 9.1 視覺要求

- 柵欄必須明確畫在格線邊界，不應看起來占據一整格。
- 可採護欄、玻璃隔板、機械圍欄或生產線防護欄。
- 視覺語彙應支持「人不能進去，但能從外部設定」。

### 9.2 互動回饋

- 玩家嘗試跨越柵欄時，應有明確阻擋回饋。
- 玩家面向柵欄另一側的方塊時，安裝提示仍應顯示。
- 首次出現時，應讓玩家不靠文字就能嘗試出「不能穿、可以安裝」。

---

## 10. 風險

1. **規則例外感**  
   若視覺不清楚，玩家可能覺得「實體不能穿，但方向可以穿」過於任意。

2. **遊戲重心偏移**  
   大量使用後，DIR 可能從玩家與方塊共同移動，偏向控制室／自動化解謎。

3. **過度硬鎖**  
   柵欄很容易直接刪除替代解，可能讓關卡只剩照順序操作。

4. **架構成本**  
   需要把 cell、object、edge 分離，並更新移動、推動、碰撞、渲染和 verifier。

5. **只是局部解法**  
   柵欄只處理玩家可達造成的漏洞，其他推法和安裝順序仍需驗證。

---

## 11. 關卡驗證清單

- [ ] 柵欄是否真的讓碰撞成為必要，而不是只縮短路徑？
- [ ] 碰撞後，玩家是否仍能從另一側接近並重新安裝？
- [ ] 方塊能否在碰撞前直接自行移動到正確位置？
- [ ] 是否存在其他方塊或方向的替代碰撞？
- [ ] 玩家第一次看到柵欄時，能否不靠文字理解「不能穿、可以安裝」？
- [ ] 玩家移動、推動、碰撞位移與 Trigger 位移是否都一致被阻擋？
- [ ] 移除柵欄後是否明顯產生替代解，證明柵欄有實質作用？
- [ ] BFS verifier 是否把 edge 狀態納入合法動作判定？

## 12. 尚未定案

| 議題 | 待決策內容 |
|---|---|
| 資料格式 | 二項邊作為唯一格式，或採「擴張格作者格式 → 二項邊 runtime」雙格式。 |
| 視覺造型 | 護欄、玻璃隔板、機械圍欄或其他表達「可操作、不可通過」的形式。 |
| 首次導入 | 直接使用柵欄彈射關，或再增加一個純安裝示範。 |
| 互動提示 | 面向柵欄後方方塊時，是否顯示特殊安裝輪廓。 |
| 後續占比 | 只支撐第二區後段，或在後續持續作為工廠／流水線語彙。 |
| 內部格式 | runtime 是否直接使用二項邊，或先以最小 `HashSet<EdgeKey>` 驗證。 |

## 目前結論

柵欄不是單純新增障礙，而是一種將「設定階段」與「執行階段」分離的邊界。

它最直接的價值是：

> 讓碰撞彈射與碰撞轉角不再依賴複雜牆型，也能阻止玩家在碰撞後親自接手。

目前最適合 DIR 的架構方向是：

```text
Terrain layer
+ Object layer
+ Edge layer
```

作者端可採擴張格邊地圖提高可讀性；runtime 與 verifier 則轉換成水平／垂直二項邊陣列。
